# 在 Cloud 看板上等没有归档日期的旧卡片满 30 天被清掉

## Setup

- **看板**：一个存储在 Cloud workspace 里的看板，归档里有 frontmatter 没有 `archived:` 日期的卡片（该字段出现前归档的，或手工放进归档的）。
- **触发**：每日清理没有命令入口，看板开着时由它的后台计时器每天跑一次。
- **本次证据的来源**：这台机器没有 Cloud 凭据，证据是对着本目录的 [stand-in.mjs](stand-in.mjs) 跑出来的：它起一个本地 HTTP 服务顶替 workspace（九张样例归档卡片，日期从今天往回推），在临时目录里放一个指向它的检出和一份虚构的登录，再调用计时器调用的同一个入口。打开看板、清理和删除请求都是这次构建自己的；没有对真实 Cloud 验证过。重现：
  1. 在 `cli/` 下构建：`node scripts/build.mjs`。
  2. `node docs/qa/skill/undated-archived-cards-expire-on-a-cloud-board/stand-in.mjs cli/dist/kanban.mjs`

## Steps

1. 打开 Cloud 看板，归档里有九张卡片。
   其中 71–74、82、92 没有 `archived:` 日期，Cloud 记录的归档时间各不相同；93 有日期。
   [01-archive.log](01-archive.log)

2. 等当天的每日清理跑完。
   - 无日期、Cloud 归档已 40 天的 71 被删除；整组最晚也已 35 天的 91（含无日期的 92）整组删除。
   - 无日期但 Cloud 归档只有 10 天的 72 留下；81 这一组因为 82 只归档了 10 天而整组留下。
   - Cloud 没有归档时间（73）或时间读不出（74）的留下，不报错。
   - 93 有 `archived:` 日期（10 天前），即使 Cloud 的时间是 40 天前也留下。
   - 只向 Cloud 发一次删除请求，Cloud 和本机副本里剩下的卡片一致。
   [02-cleanup.log](02-cleanup.log)

3. 同一天看板继续开着，计时器再跑一轮。
   不再发删除请求，归档不变。
   [03-second-pass.log](03-second-pass.log)

## Feedback

- **结果符合直觉**：无日期的旧卡片终于会到期，同组卡片一起走，用户不用做任何事。
- **完全无声**：卡片被删时界面和终端都没有任何提示，归档里少了哪几张、为什么少，事后无从得知；30 天这条规则只写在文档里。
- **读不出时间的卡片永远留着**：Cloud 没有归档时间的无日期卡片每天都按「今天刚归档」算，不会到期，也没有地方告诉用户有这样的卡片；它所在的整组也跟着一直留下。
- **导入的旧卡片会多留 30 天**：从别的看板导入的无日期卡片按导入时刻算，对用户来说是「明明很旧却还在」，只能等。
- **等不了，也试不了**：清理一天只跑一次、没有命令可以手动触发或预览，想确认它是否生效只能第二天再看归档。
- **未在真实 Cloud 上验证**：证据来自顶替的 workspace；真实服务返回的 `archivedAt` 格式与删除接口的行为没有在这里核对过。
