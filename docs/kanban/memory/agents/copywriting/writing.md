# Writing

## Shared

- **润色用户原稿只顺字句**：保留原意和用户特意要讲的概念（如「关键点」「持续学习」），只改标点、生硬词和错字；创始人自述等原话不加小标题、口号或推销结尾，读起来要像人写的。
- **由一种语言改写成另一种**：写出原文本意，不逐字直译、不沿用原文句式；逐段对齐已定稿的那一版（含已确认的 UI 稿），不增删论点或板块。
- **中文用正式、易懂的书面语**：不用口语化或生造的说法（如「带你的人」「现成团队」），直接写具体行为（如「内置专业 agent」）；不加说不清用意的修饰（如「独立的」）；栏目名用常见的正式叫法（如「导师介绍」）。
- **开头一句话讲清前提**：细节放后面；段首不突然接没铺垫的事；句子短，无歧义。
- **固定说法**：用户可「创建自定义智能体和工作流」（不说「调整角色」）；记忆写「偏好和决策」；中文用小写「agent」，不用「智能体」，角色写「设计 agent」「文案 agent」；数量写「10+ agent」；中文稿里的英文内容类型也要译；AI4Kanban 是工作区，不写成计划生成器。
- **只用界面上的名词**：不造「Task state」「shared decisions」之类的词；跨卡延续的决定叫 project memory 并链 `/docs/memory`；提醒叫 notification；英文写 specialist agents，单写 specialists 像真人；页面不写 ui-designer、copywriting 这类内部代号。
- **agent 自动加入**：规划时看板按卡片要改的东西自动请来对应 agent，不写成要用户点名。
- **草稿是定稿，不是「方向」**：agent 只在需要用户拍板的部分先出最终版本，构建照它做、不漂移，其余 agent 直接做；人看草稿是「审」「把关」「改掉问题」，想法不对时可直接放弃这张卡；不写「你定方向」「approve the direction」；类型写 UI、文案、视频脚本等，不分 key/non-key。
- **审完草稿就交付**：不写人还要检查交付、对照草稿验收或逐项看成品。
- **稿件可直接套用**：不写「替换某段」这类修改说明；Markdown 镜像、`llms.txt` 同步采用正文那份稿，只单列镜像独有的改动。
- **每页只讲本页主题**：Workflows 文档只讲各工作流做什么、怎么选、怎么自定义；下载页只说下载什么、适合谁、支持哪些平台；定价页导语只说各方案的共同前提；不硬塞产品定位或卖点；说不出具体内容的句子宁可删掉。

## Promotional copy

- **为什么是独立开发者的 Agent 工作台**：①开发、营销多工作流各有专业 agent 团队，共享项目上下文，越用越专业；②草稿只抽出要人精确把关的部分，审完把细节真正交出去；③自动拆成独立任务，紧急的先交付。草稿只是其一，不是全部价值。
- **首页定位**：中文「独立开发者的 Agent 工作台」，英文「Agent workspace for indie hackers」，用户指定的说法原样保留；分享标题沿用主标题。
- **卖价值，不卖功能**：先讲用户省下什么——不用每个细节都亲自盯、人只审要点，一天交付更多；澄清想法、工作流这类机制是「怎么做到」的依据，不当价值写进首屏，细节留给对比表。
- **价值优先，也要讲出差异**：不用「什么都能交给 agent」这类同质承诺，首屏要让人看出草稿这个差异点；标题讲价值，不列支持的 agent（用 logo 栏表现）。
- **首屏标题要有力、有网感**：口语、具体、有记忆点，长度适中；副标题同样重要，讲草稿和用户的收益，不罗列草稿类型或场景清单；中文大标题不加句末标点，用换行代替逗号；用轻而具体的词，不用「the right things」这类含糊指代，也不用 judgment、handle execution 这类偏重或管理腔的词。
- **开箱即用是首要卖点**：内置专业 agent、工作流和记忆管理，不用自己设计分工或反复调 Prompt；首页不写 Pro 标记或付费范围；开源 README 不提 Pro。
- **首页入口是应用**：首屏给下载与 GitHub，底部从桌面应用开始；首屏已有的内容（如安装）不再单开一段。
- **演示里的示例任务要具体**：每条写清做什么、带具体对象（如「30 秒 v2 宣传片」），不为了短写成「制作宣传视频」这类泛称。
- **落地页说人话**：页面文字短而准；不把 agent 的内部规则或配置细节写给访客；一个东西只用一个叫法；流程能用图讲就不写长段，不讲具体案例故事。
- **对象是有偏向的人群**：面向愿意把执行细节交给 agent、自己把关关键决定的人；不写「有主见」，不强调「通用工具」「不改变工作方式」。
- **规划离不开用户**：不说「全交给智能体」或「一句话→几个问题→计划」；「不用盯着」只限执行阶段，小任务可跳过规划直接实现。
- **拆卡的说法**：复杂想法拆成边界清楚的独立卡片，每张在自己的会话里规划，上下文不混；高度相关的子任务组成 group task，父卡是共享上下文；交付顺序的规则不展开写。
- **编码页的叙事**：一项工作大部分时间在反复改几个关键点，所以一开始就把关键点提到卡片上审完；视觉草稿胜过纯文字的 plan mode，不用开 dev server。
- **草稿从用户的顾虑讲起**：凡是担心 AI 自由发挥的部分都可先出草稿预览；格式有图片、图表、HTML/TSX、diff、storyboard。
- **记忆和跟进的说法**：每个 agent 有按自身场景设计的记忆，学用户对特定任务的偏好和决定，agent 间也能共享；跟进写「完成一项主线工作后，agent 自主提出跟进项，帮你补缺补漏」。
- **agents 介绍页**：标题用问句；只列一部分实际的 agent 并链完整文档；琐碎功能细节（如多模型选择）收进 FAQ。
- **FAQ 只收访客真会问的**。
- **与 Codex 等编码 agent 的关系**：AI4Kanban 是人和编码 agent 之间的中间层，它们是执行层，不是对手；对方已有的计划、子 agent、skills、记忆、定时任务不写成我方独有；skills 是执行用的 SOP，工作流承载「什么需要人关注」和易审的草稿，两者互补。
- **对手写成另一种可行方式**：不贬低，不在对手之间下结论；我们审的是执行前的草稿，不和对手的代码审阅并称「审阅」。
- **对比只写内置有没有**：每项写「有／没有」或「只能…不能…」，不用「取决于配置」绕开；双方都有的（任务拆解、依赖管理、CLI）归共同能力。
- **对比页摘要要客观**：description、social 与首屏导语共用一句「比较对象＋具体维度」，不写成己方广告；价值和选谁留给正文。
- **不写自我否定的分析**：实测结论只用正面可证的部分。
- **创始人页讲真实的项目演进**：以用户的故事稿为准，写尝试、反馈和转向；第一人称，可带少量口语；不拿履历代替故事，不编日期、对话或数字。
- **draft-first 与主产品无关**：AI4Kanban 的页面不介绍 draft-first，也不把它当入口。
- **draft-first 的核心词是「草稿」**：先审草稿，不偷换成「审结果」，也没有「decision」。

## Docs

- **只说能不能设置、在哪设置**：不写默认值。
- **文档是操作指南**：按步骤讲怎么做，不写成对比文章；各工具的安装只链其官方文档。
- **教程以交付为终点**：讲从想法到交付并试用成品，草稿只是中间一步。
- **每一步配截图**：截图紧邻该步说明；有演示视频也不能只放视频；概览页也配图，可复用其他文档页的截图。
- **讲设置项顺带讲它怎么工作**：先讲帮用户省下什么，再简述何时发生、结果在哪看、谁来决定，让用户判断要不要关；只写用户看得到的部分。
- **用词**：接入的是 coding agent，不写 coding tool；支持多种运行环境叫 multi-runtime support；「交给」要写明交给谁。
- **卡片对话主要用来改草稿**：也可提问、回答问题、开始构建；不把改范围、改版本、归档写成主要用途。
- **记忆分三套**：项目记忆、agent 记忆、多 agent 共享的全局记忆；内置工作流已定义好记忆，自建 agent 要在说明里写明怎么记；回顾对话、整理记忆周期自动运行，需要时才手动跑。
