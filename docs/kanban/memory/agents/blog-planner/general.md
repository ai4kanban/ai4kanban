# General

## Claims

- **只写有依据的说法**：不承诺未经测量的效果，不把我们自己的经验说成读者的情况或普遍规律；有原稿时只用原稿的观点和例子，篇幅不比原稿臃肿。
- **引用要支撑论点**：数据、论文或原句必须直接支撑所在句，仅仅相关就删或换，外部来源只留支撑核心论点的少数几个；关于 Agent 能力的判断加 today's 之类的时间限定；社区观点引最直接的原帖，并附原帖截图。
- **时间按实际投入算**：人的时间按实际动手算，AI 按执行时间算，不用含等待的挂钟时间。
- **例子要有来龙去脉**：优先用 AI4Kanban 自己的真实做法（如卡片元数据校验、这篇文章本身的产出过程），先交代背景；不举看不出为什么是例子的需求句或孤立的规则清单。
- **按产品真实行为写**：自动发生的步骤（规划、出草稿）不写成人去叫 agent 做。

## Structure

- **按读者的问题分节**：每节回答读者会问的一个问题，接住上一节的结论；节标题优先用问句（利于 GEO、引人思考，非硬性），问 what 就答 what。
- **主题逻辑优先于宣传**：先讲完主题（是什么、现状、痛点、办法、局限），产品只作办法里的例子并写明是举例；不插断主线的宣传节，不加下载号召、自荐内链这类硬广句。
- **标题连贯优先于关键词**：标题、dek、H2 围绕主线，不用「关键词: xxx」式标题；用户给的示例标题只是方向，先评估再提议；措辞贴合主张，不夸大。
- **讲要点不写工作日志**：几轮修订合成一步，只说给了几轮反馈、得到什么；对比表只留影响选择的几项，不做竞品调研式罗列，不放无关数据（如 token 用量）。
- **不定字数**：规划时不指定篇幅，内容讲完即止。

## Voice

- **保留人的语气**：润色只修生硬的词，保留短句和停顿，不磨成「专业但像 AI」的顺滑文字；不用似是而非的习语；人与 Agent 对比用 humans，不用 people。
- **说清具体结果**：每句写明对谁、做什么、有什么后果，不写 “walls of text stop working” 这类说不清对什么失效的话；开头用具体真实的场景（如 `/goal` 跑两小时、返工两天）。
- **亲历类用故事叙述**：How we built 这类文章用第一人称真实经历，不写成研究报告；但清晰优先，已讲清楚的说法（如 First/Second）不为口语化而改。
- **删赘述不硬缩句**：标题已是总结，开头两三句直接进正文，不复述全文，不引用我们之前的文章；不写复述上文的总结句，人物第二次出现只写名字；但不压掉主语和衔接，句子要通顺完整。
- **术语写成具体的东西**：读者未必懂的词（如 instruction files）直接写成 `CLAUDE.md` 这类实物，和本节无关就不提。
- **不用脏话**：用户反馈里的情绪改写成平实说法（如 a UI you’re not satisfied with）。
