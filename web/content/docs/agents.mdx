Every flow the board starts is run by a named **agent**, and each one has a page: its rule, what
it remembers, its settings, and — for one you added — its own instructions. Where you reach that
page says who assigns the agent. **Configuration → Workflows** picks a workflow, steps through its
plan, execute and review stages, and lists the agents each stage assigns. **Configuration → Board**
lists the agents the board runs itself, which no workflow assigns and every workflow gets.

There are two kinds.

**Roles** are the agents the board's own flows are run by. You do not add or remove one, and some
of them can be switched off:

- **Software planner** (`software-planner`, `planner` before) — plans and refines the Coding
  workflow's cards. It runs create, refine, resolve, revise, the release
  plan, the changelog, archive and reject.
- **Builder** — builds cards and lands them: implement, conflict, run.
- **Scriptwriter** — leads the Product video workflow: a product intro, a screen demo, or both.
  It writes the script — audience, core claim, the story in viewing order, the exact narration
  and on-screen text, and the product facts with how each was checked — plus, only for a demo, the
  actions to show and what each should look like. A real demo goes in only when you ask for one or
  it shows the point better than screenshots, animation or text. You approve the script once;
  changing it needs your approval again, and the Decider never approves for you.
- **Deck planner**, **Deck builder** — lead the Slide deck workflow. The planner works in two
  rounds and waits for your approval after each: first the content — audience, goal, facts,
  design and every slide's copy — then a real preview of every slide. A content change sends it
  back to the first round; a visual-only change redraws just the slides it touches. Once you
  approve both, the builder makes an editable `.pptx`, checks it against the approved previews,
  and puts a download on the card.
- **Sweeper** — settles a card that has sat too long: it rewrites the card for the project as it
  stands today, or discards it. `akb card unstick <id>` runs it on one card.
- **Gater** — judges whether a card that reached ready is clear enough to build unwatched. Off by
  default.
- **Decider** — answers the questions on a card that are waiting on you. Off by default.
- **Proposer** — reads a card the board has just finished and proposes the work that should follow
  it. Off by default.
- **Triage** — sorts what is waiting in Triage into cards and ignores. Switched on, it sorts each
  batch of new items itself and keeps going until nothing is waiting; `akb triage run` sorts either
  way. Off by default. Boards with [Triage](/docs/triage) open only, and it is not on the roster at
  all where Triage is closed.
- **Memory pruner** — squeezes the memory back down to what helps planning. **Run now** on its page
  starts one; a recurring prune is opt-in there, with a cadence, and off by default.
- **Review chat memory** — reads back over the conversations that said something new and writes
  down what they settled. On by default, once a day.

The Gater, the Decider, the Proposer and the Triage agent are the four that are off until you ask:
none of them does a flow's work, each spends a run you never asked for, and each reads the whole
board — the goal, and the planner's `decisions.md` and `rejected.md` — on top of the card. Review
chat memory is the one switch that goes the other way, and the one that asks before it goes **off**
rather than on.

**Specialists** fill one part of a card's spec and fill only that part. Each one runs on its own,
while a card is being planned — never while it is being built — writes one named section of that
card, and changes nothing else. The board ships four, and `akb spec` lists them:

- **`copywriting`** — writes the promotional copy a card changes: website pages, the README,
  release notes, and store or Product Hunt listings. User documentation, text inside the product
  and social posts are not its job. It writes the final copy and leaves one question asking you
  to confirm it.
- **`ui-designer`** — draws the screen a card needs as one design, one drawing per page or state
  it changes and each named for what it shows, with nothing written under the drawings. Every
  **mockup** is a rendered screen — a copy of the product's own screen, true to the real UI. See
  "Assets on a card" in `kanban-ui/README.md`. On a card that has copy, it waits until you have
  confirmed the copy and then uses it word for word.
- **`tech-stack-advisor`** — picks the library, tool, or service a card leans on. Its answer is
  one table — a row per candidate, with what it is, its pros and its cons — and one line naming
  the pick. Keeping what the project already uses and writing it yourself are rows too, so a card
  doesn't come back with something new to install by default.
- **`hyperframes-editor`** (Video editor) — on a Product video card only, after you approve the
  script: makes the film while the card is still being planned. It picks its own method
  (HyperFrames by default), captures the real product, generates the narration, renders on your
  machine, then watches and listens to check facts, readability, pacing, sound and anything
  private on screen. The playable video lands on the card with the command that renders it again.

A specialist's run is a run like any other, with three things that make it different: it starts
clean, given the card and a short note but never the conversation that asked for it; it writes one
named section — ``## By `ui-designer` agent`` — and nothing else, rewritten rather than doubled on a
second run; and nothing waits for it, so a planning flow carries on and the section arrives when it
is done. When the answer is a pick only you can make, it leaves an open question instead of choosing.

You rarely ask for one yourself — the flow working the card asks when the card needs it, after a
card is added, after a refine or revise that moved the screen or the library, and never from a
release plan (each card's own refine asks instead). A card that needs neither a
screen nor a library goes through all of those without a spec run, and nothing tells you it did.

**Reviewers** check what a build delivered. A workflow's review stage is a list of reviewers
with no lead: after each build, the board reads the diff, picks every reviewer whose description
matches what it touches — the first on the list when none does — and reviews as each of them in
one run. The board ships **`code-reviewer`**, which reviews any delivery that changes code and is
the Coding workflow's reviewer. Add your own under **Configuration → Workflows**, in the review
stage. A workflow with no reviewers delivers a finished build as is, and **Review every build**
under **General → Delivery** turns review off for every workflow.

A Product video has no build and no review: the card shows **Archive** once the film is ready,
and archiving it is how you accept it. **Revise** changes it instead — a script change needs your
approval again, a film-only change keeps the script and renders again — and Archive returns when
the revision is done.

When you do want one: **"put the ui-designer agent on #4"**, or `akb spec ui-designer 4`. Whether
it joins a card's planning at all is its workflow's plan stage, under **Configuration → Workflows**:
add it there and it is offered, remove it and nothing asks for it. Setting what it produces is on
its page, beside that same list. A role is always on except the ones above, because a board without
nobody plans anything.

## Let the Decider answer for you

A card that reaches the end of its planning with nothing but `[user]` questions on it stops and
waits for you. So does a delivery a review sends back with a question. **Decider** is the switch
that removes both waits: it answers those questions in your place and the card carries on.

Switch it on in **Configuration → Board**, in the **Automatic** group. It asks once before it goes
on, because it is the most expensive switch on the board:

> **While this is on, nothing stops for you.** An idea runs all the way to landed without asking
> you — a wrong direction included. What it chose, you read afterwards on the card.

It answers from the project's goal, the planner's `decisions.md`, and the
recommendation each question carries — in that order. When none of those settles a question it
takes the recommendation anyway: every recommended option on a multi-choice question, the first
option when nothing is recommended, and its own answer on a question with no options. It never
hands a card back.

What it chose stays on the card, in a `decided:` list — the question, the option it took, and the
file it went on. The board marks such a card and **What Decider chose for you** on the card page
lists them one by one, with the ones it took blind called out. None of it becomes a lasting
decision: planning's `decisions.md` holds answers *you* gave, and the Decider writes to none
of it.

Switching it off puts every card still carrying questions back to waiting on you. A card it
already answered and the board already built does not come back. Switching it on changes nothing
that is already stopped — those cards move on their next refine, or when you type
`akb card decide <id>`, which runs it on one card whether or not the switch is on.

## Let the Proposer look back

Nothing on the board looks at finished work. A follow-up surfaces only when a build or a plan
notices one mid-task, and **Triage** reads outside sources — never your own history.

**Proposer** is the switch that closes that gap. Switch it on in **Configuration → Board**, in the
**Automatic** group. From then on, every card that reaches the archive starts one reflection over
that card alone: it reads what shipped, judges what work follows from it against your goal and the
planning memory, and puts each survivor in **Triage**.

- **Archiving is the only trigger.** A card completing is what starts a reflection. Nothing sweeps
  the cards you finished last week, and there is no command that asks for one.
- **One run per completion.** That is what it costs while it is on, and the whole of what it costs.
- **It proposes into Triage, never onto the board.** A proposal is triaged like anything else
  that arrives there, so a weak one costs you a dismissal rather than a card in your backlog.
- **It grounds every proposal.** Anything already planned, already in Triage, or in a
  `rejected.md` is skipped. Finding nothing worth proposing is a normal result, and the common one.

Each item it writes carries a short rationale and the card that prompted it, so you can read what
the proposal came from before deciding. Switching the Proposer off leaves nothing behind — items
already in Triage stay there, like any other.

## Let Triage sort for you

**Triage** is the switch that empties the list you would otherwise read. Off, items wait until you
type `akb triage run`. On, a batch of new items starts one sort by itself, and that sort's close
starts the next until nothing is waiting.

- **A new item is the only trigger.** A pull, **Add** on the page and `akb triage add` alike, so
  what the Proposer writes is judged like anything from outside. Switching it on sweeps nothing
  that is already waiting.
- **One sort per batch, plus one more per sort that judged something.** A sort that judged nothing,
  one that failed, and one you stopped all end the chain rather than starting another.
- **Each card it writes carries a refine.** That is what it costs beyond the sort itself, and the
  reason the switch asks once before it goes on.

Running it alongside the Gater and the Decider is not recommended, and the board does not stop you:
with all three on, an item somebody outside your team wrote can go from Triage to built without one
human confirmation. [Triage](/docs/triage) has the whole of what a sort does.

## Let the memory review remember for you

A chat used to judge each turn as it landed: was this a preference worth remembering? One turn
cannot see where a conversation is going, so a "what if" you threw out and took back three turns
later could land in `decisions.md` as a decision — while the real conclusion of a long discussion
was never written down at all.

**Review chat memory** is what writes it down instead. Chats no longer save memory. Once a day it
reads every conversation that has said something new — a card's chat and a discussion alike — right
through, and writes what the whole exchange earned.

- **A day at most behind.** Memory only feeds future planning; the card you are talking about was
  already changed in the conversation.
- **It rewrites rather than repeats.** Reading the whole conversation is what lets it correct a
  note from last week that you have since overturned, instead of leaving both.
- **"Don't record this" holds.** Say it in the conversation and nothing is written — and a note an
  earlier review already wrote is deleted.
- **Nothing said, nothing run.** It starts only when a conversation has new messages, so a quiet
  day costs nothing.
- **It follows the conversation's card.** A note goes in the planning memory, under the
  `## <module>` topic that card's `modules:` names — the archive included. A discussion, or a card
  the board no longer has, goes under whatever topic already fits.

It is on by default, which no other self-starting agent is: it took over what a chat was doing
unconditionally, so a board that had to ask for it would be a board that quietly stopped
remembering. For the same reason its switch asks before it goes **off** rather than on. **Review
now** on its page asks for one at any time, switch or no switch, and `akb review-memory` is the
same entry from a terminal. What each review wrote is in its run log.

## Give an agent a rule

A **rule** is one paragraph, in your own words, added to the **end** of every run that agent does,
after everything the board writes into it. Write it in the box on the agent's page; it saves when
you leave the box.

- **It is plain words, not a command the board runs.** What it actually causes is up to the agent
  reading it. On the Code reviewer, a check your rule asks for is one of the repository's checks.
- **It belongs to the agent, not to one flow.** One rule on the Builder reaches implement, conflict
  and run alike, so a convention you write once is followed everywhere that agent works.
- **It lives in your board**, at `docs/kanban/rules/<agent>.md`, tracked in git — so a team shares
  it and a run started from a terminal reads the same words. Clearing the box deletes the file.
- **A delivery freezes the rules it starts with**, so editing one changes the next delivery and
  never one in flight.
- **Every session that agent starts reads it**, so a long rule makes every card slower.

From a terminal: `akb raw rule <agent> --file <path>`, or `--text ""` to clear it.

## Give an agent memory

Some agents **remember** — the taste they were corrected on, and the choices you made. The
agent's page lists the files it has, read-only:

- **Planning** keeps three files in `docs/kanban/memory/agents/planner/`: `decisions.md`,
  `rejected.md` and `redesign.md`. Whoever leads a plan stage writes them;
  the Gate, the Decider and the Proposer read them and write none. No other role owns a file.
- An **agent** owns `docs/kanban/memory/agents/<name>/`, and its own `AGENT.md` says which
  files it keeps there and what each holds.
  `ui-designer` keeps `redesign.md` and `decisions.md`, `copywriting` keeps `writing.md`, and
  `tech-stack-advisor` keeps none. A specialist is handed every file in its folder on each run.
- **The deck planner remembers your feedback** in `feedback.md`, so the next deck starts from it.
- **The video agents remember your feedback.** Tell the scriptwriter or the video editor what to
  do differently and the next video starts from it; one video's change is not a general rule.
  Nothing you say is written back into a recipe. Long feedback is split
  into `feedback/<topic>.md`; the Memory panel lists those files under **Feedback**, and the
  index in `feedback.md` links to them.
- **The board's own record is nobody's memory.** `docs/kanban/memory/readme.md` — what shipped —
  and `goal.md` are facts rather than taste, so they sit outside every agent's folder.
- **How the product looks is not memory.** Colours, dimensions and component detail are read from
  the app's own `design.md`, so memory says which doc to read rather than repeating it.
- The runs write these themselves — the flow that hears your answer records what was taken or sent
  back, and the agent curates the files on its own runs. Nothing on the pane edits one.

## Add one of your own

Creating a custom agent requires the [AI4Kanban skill](/docs/daily-loop) in your project and the
[`akb` CLI](/docs#install-the-board). Follow the linked setup instructions if either is missing.

In your project's coding agent session, describe the agent you need:

```text
Use the AI4Kanban skill. Read akb guide write-agent,
then create an agent that [describe its job].
```

That guide is the one place the file is written from — its name, its description, the files beside
it and the translations it carries — so what comes back is an agent this board accepts.
`akb spec` lists the agents this board can use and, under them, anything wrong with one it found.

**Add helper → Create one** in Configuration → Workflows starts one from the board instead: it
asks for a name, writes the folder under `docs/kanban/agents/`, assigns it to the stage you were
looking at, and opens the new agent's page with its instructions box focused. A name a role or a
bundled agent already answers to is refused in place. The whole file is the box on that page,
frontmatter included, and a save the board would refuse
keeps your text and says what is wrong rather than leaving an agent it cannot read — the pane and
the file are one thing.

A new agent **helps** a stage. It can be written to **lead** a plan or execute stage instead, and
one that can lead is only offered as a workflow's lead, never as a helper. Of the ones the board
ships, the Software planner, the Builder and the Scriptwriter lead. A workflow that already has
an undeclared agent leading, or a lead among its helpers, keeps running until you change it, and
Configuration → Workflows marks an undeclared lead.

**Delete** on an agent's page removes it and everything the board kept for it — the folder, the
instructions you wrote for it, what it remembered, and its switch. Only an agent this project
added: the roles and the three the command ships are not yours to remove, and have no Delete.
