Claude Code already has subagents, agent view, agent teams, task lists, and Git worktrees. Those tools help Claude execute and coordinate work. They do not decide which product ideas are ready, which assumptions must be settled first, or which decisions should guide the next session.

AI4Kanban manages that project-level state, then gives implementation to your existing Claude Code CLI.

## Why use a kanban when Claude Code already runs agents in parallel?

[Claude Code can parallelize work with subagents, agent view, agent teams, worktrees, and batch operations](https://code.claude.com/docs/en/agents). Each solves an execution problem. AI4Kanban handles the planning state around that execution.

| Claude Code gives you | AI4Kanban adds |
| --- | --- |
| Subagents for bounded work inside a session | A requirement that is settled before the session delegates |
| Agent teams with a shared task list | A repository-level backlog that survives the team and its lead |
| Agent view for running sessions | Readiness, product questions, dependencies, and delivery review |
| Worktrees that isolate file edits | Scheduling, landing order, conflict handling, and re-review |
| Conversation context and auto memory | Curated product decisions shared with future tasks |

Claude Code's native task list coordinates the workers in an active team. A board card is the durable product contract: why the work exists, what it must accomplish, what blocks it, and how completion will be verified.

## Does a board improve Claude Code's output, or only track it?

It improves the input Claude receives. A card is refined against the repository, the project goal, prior decisions, related work, and the code that already exists before implementation begins.

| During refinement | What happens |
| --- | --- |
| The request is broad | It becomes a concrete outcome, scope, and acceptance criteria |
| A factual question appears | Claude investigates the repository and settles it from evidence |
| A product choice affects behavior or risk | The card stops with concrete options and a recommendation |
| The work is too large | It becomes subtasks with explicit dependencies |

That reduces plan drift because the implementation session starts from a reviewed requirement instead of reconstructing intent from a rough prompt.

## Can Claude turn a rough idea into a build-ready task first?

Yes. Add a sentence to the board and run refinement. Claude reads the relevant code and planning context, answers what it safely can, and records its reasoning on the card.

The task becomes ready when its outcome, boundaries, dependencies, edge cases, and verification criteria are clear. If the remaining uncertainty requires product judgment, the card waits for you instead of letting implementation guess.

## How does the plan survive compaction, `/clear`, and new sessions?

The important state does not depend on the chat transcript.

| Durable state | Where it lives |
| --- | --- |
| Approved requirement and verification criteria | The Markdown card |
| Active implementation and its exact approved input | The delivery record |
| Current product decisions | `decisions.md` |
| Ideas that should not return | `rejected.md` |
| Design corrections to remember | `redesign.md` |
| Shipped user-facing behavior | `readme.md` |

The four memory files exist for the project and for each named module. A new run loads the card plus only the relevant project and module memory. It does not need the whole transcript or the whole history of the repository.

## Can several Claude Code tasks run without mixing their changes?

Yes. Each automatic delivery gets its own branch and Git worktree. Known dependencies stop blocked cards from starting; independent cards can build together.

Worktree isolation prevents sessions from editing the same checkout. It cannot guarantee that two valid branches still compose. AI4Kanban handles that later: reviewed deliveries enter one landing queue, are squashed and rebased onto the current target branch, and are reviewed again whenever the rebase changes the tree. A real conflict becomes a focused resolution run and the composed result is reviewed before landing.

## Where does the human stay in control?

Different pauses mean different things.

| Moment | Who decides |
| --- | --- |
| Repository fact or routine implementation detail | Claude researches and decides |
| Consequential product ambiguity | You answer before implementation |
| Requirement is ready to build | You approve Implement |
| Implementation matches the approved card | A fresh Claude Code session reviews it |
| Reviewed diff may land | Automatic, or you approve it when diff approval is enabled |
| Target branch may be pushed | You; AI4Kanban never pushes |

Bookkeeping can advance automatically: card status, dependency unblocking, review, rebasing, landing, and worktree cleanup. Product judgment and any approval checkpoint you enable still stop for you.

## How do I know when Claude Code needs me?

Questions and review requests appear in the app and can be sent to Slack. Running, failed, and landed cards have distinct states, so a completed turn is not confused with a request for input. Other deliveries keep moving while one card waits.

## Does it replace my Claude Code setup?

No. AI4Kanban launches your installed Claude Code CLI. Your model login, `CLAUDE.md`, rules, skills, hooks, MCP servers, permissions, and project commands continue to apply. Claude Code runs under your existing permission settings; denied tool calls remain visible in the run log.

[Claude Code loads each extension at a different point in its context](https://code.claude.com/docs/en/features-overview). AI4Kanban invokes its board skill directly, then supplies the card and scoped project memory for that workflow.

Choose a Claude subscription, an Anthropic API key, or an Anthropic-compatible endpoint. Named runtimes can use different models and reasoning effort for refinement, implementation, review, and specialist work. Empty fields keep Claude Code's defaults.

<FAQ title="Frequently asked questions">

<FAQItem question="Does AI4Kanban use my Claude subscription, or do I need an Anthropic API key?">

Both work. Use the login already held by your Claude CLI, an Anthropic API key, or an Anthropic-compatible gateway. The selected provider is explicit, so a saved API key does not silently replace a subscription run.

</FAQItem>

<FAQItem question="Can I choose the Claude model used for planning, implementation, review, and testing?">

Yes. Create named Claude Code runtimes with their own model and reasoning effort, then bind them to board workflows. Tests run inside the implementation and review workflows rather than as a separate testing stage. Empty settings keep Claude Code's defaults.

</FAQItem>

<FAQItem question="Does AI4Kanban require an MCP server?">

No. The local app invokes Claude Code and its `/kanban` skill directly. Your existing MCP servers remain available to Claude when a task needs them.

</FAQItem>

<FAQItem question="How much context overhead does the board add?">

There is no fixed token number: card and memory size vary. A run receives the approved task, the workflow instructions, project memory, and memory for the card's named modules. It does not load every card or replay the board's full chat history.

</FAQItem>

<FAQItem question="Can Claude create cards, subtasks, dependencies, and status updates itself?">

Yes. The board skill gives Claude structured commands for creating and refining cards, splitting groups into subtasks, recording dependencies, answering questions, and moving work through its lifecycle.

</FAQItem>

<FAQItem question="Can a board task use Claude Code subagents or agent teams?">

Yes, when your Claude Code configuration and permissions allow them. They remain execution tools inside one board delivery; the approved card, branch, review, and final status stay attached to that delivery. [Agent teams are a native Claude Code feature with their own shared task list](https://code.claude.com/docs/en/agent-teams), not a replacement for the project board.

</FAQItem>

<FAQItem question="What is the difference between a board task, a Claude session, and Claude Code's task list?">

A board task is the durable product requirement. A Claude session is one refinement, implementation, review, or correction conversation. Claude Code's native task list coordinates workers inside an active agent team. Several sessions can contribute to one board task, and the board task remains after those sessions end.

</FAQItem>

<FAQItem question="Can I resume the same Claude Code session from a card?">

Yes. A failed run keeps its Claude session ID and delivery. Resume continues that conversation with the worktree and card state intact instead of starting over.

</FAQItem>

<FAQItem question="What happens if Claude reaches a usage limit or stops halfway through?">

Claude Code rate limits end the run and free the card instead of holding it through a long retry. The card, delivery, worktree, and resumable session remain available. A configurable silence timeout handles runs that stop producing output.

</FAQItem>

<FAQItem question="Can Claude work in my main checkout instead of an isolated worktree?">

Yes. Disable automatic Git commits globally or for one delivery. Claude then works in the current checkout and you handle the commit after review.

</FAQItem>

<FAQItem question="How are .env files, dependencies, databases, Docker resources, and ports handled in worktrees?">

A delivery worktree begins with tracked files. Put repeatable dependency and local-environment setup in the implementation rules. Ignored files are not copied automatically, and host resources such as ports, databases, and Docker names are still shared, so give parallel deliveries distinct values when the project needs them. Agent credentials stay in the ignored `docs/kanban/.env` file.

</FAQItem>

<FAQItem question="What if parallel tasks invalidate each other's assumptions or conflict when they land?">

Dependencies prevent conflicts you can predict. For changes discovered later, the landing queue rebases each reviewed delivery onto the current target branch. Clean rebases are reviewed again; real conflicts get a focused resolution run and another review before landing.

</FAQItem>

<FAQItem question="Who runs tests and decides that a task is done?">

The implementation run follows the card's verification criteria, and a fresh review session checks the requirement and diff, fixes plain mistakes, and reruns focused tests. Passing tests are evidence; the approved card defines done. Enable diff approval when you want the final judgment yourself.

</FAQItem>

<FAQItem question="Will Claude commit, merge, push, or delete a worktree without my approval?">

Approving Implement authorizes automatic commits, one reviewed squash landing, and cleanup of that delivery's branch and worktree after it lands. Enable diff approval for a second checkpoint, or disable automatic Git commits to manage Git yourself. AI4Kanban never pushes.

</FAQItem>

<FAQItem question="Can I use the same board with Codex, Cursor, OpenCode, or another coding agent later?">

Yes. Cards, dependencies, requirements, and project memory are agent-independent. Pick another supported runtime for new work. An existing resumable conversation remains tied to the agent that created it.

</FAQItem>

</FAQ>
